# revmc JIT 性能分析：为什么 JIT 只有 1.02x 加速

## 摘要

revmc 是一个 EVM 字节码 AOT/JIT 编译器，通过 LLVM 将 EVM 操作码编译为原生 x86_64 代码。基于来自 Base 主网区块 38014931 的 400 笔真实交易的基准测试（jsonl_bench）显示，相比原生 revm 解释器仅有 1.02-1.04x 的加速。本文档分析了低加速的根本原因、架构限制和优化建议。

## 第 1 节：基准测试结果摘要

**基准测试参数**
- 数据源：Base 主网区块 38014931
- 交易数：400 笔（跳过 6 笔）
- 工具：jsonl_bench（JSONL 格式的基准测试工具）

**整体性能**
- Native 解释器：48.60ms
- JIT 编译版本：47.44ms
- 加速比：1.02x
- 中位数加速：1.25x（~70% 的交易更快）

**性能分布统计**
| 加速比范围 | 交易数 | 占比 |
|-----------|--------|------|
| <0.5x (JIT 明显更慢) | 29 | 7.3% |
| 0.5-0.8x | 50 | 12.5% |
| 0.8-1.0x | 39 | 9.8% |
| 1.0-1.3x | 106 | 26.5% |
| 1.3-1.5x | 102 | 25.5% |
| 1.5-2.0x | 63 | 15.8% |
| >2.0x | 11 | 2.8% |

**关键观察**
- **30% 的交易在 JIT 下反而变慢**（加速比 <1.0x）
- 279 笔更快的交易总共获得 ~7.77ms 的收益
- 118 笔更慢的交易总共损失 ~6.61ms
- 净增益仅 ~1.16ms，导致整体加速比为 1.02x
- 即使排除前 20 笔冷启动交易，加速比仍仅为 1.04x

## 第 2 节：架构分析 - JIT 能和不能优化什么

### JIT 内联优化的操作码

JIT 编译器将以下操作码内联为原生指令（这是 **唯一获得性能收益的部分**）：

**算术操作**（translate.rs:679-704）
- ADD, MUL, SUB, DIV, SDIV, MOD, SMOD
- 内联为单条或少数几条 x86_64 指令

**比较操作**（translate.rs:724-744）
- LT, GT, EQ, SLT, SGT, ISZERO

**位操作**（translate.rs:745-748）
- AND, OR, XOR, NOT

**移位操作**（translate.rs:754-761）
- SHL, SHR, SAR

**栈操作**（translate.rs:983-997）
- PUSH, DUP, SWAP

**性能影响**：这些操作在真实世界 EVM 执行中仅占 5-15% 的运行时间。

### 通过 extern "C" 内置函数调用的操作码

所有其他操作码与解释器使用 **相同的代码路径** — 通过 extern "C" builtin 调用：

| 操作类别 | 操作码示例 | 占执行时间（估计） | 原因 |
|---------|----------|-----------------|------|
| **存储** | SLOAD, SSTORE | 30-50% | 通过 host trait 的 HashMap 查找（本 benchmark 使用 CacheDB） |
| **调用** | CALL, STATICCALL, DELEGATECALL, CREATE | 15-20% | 暂停执行，跨合约调用 |
| **内存** | MLOAD, MSTORE | 10-15% | 当前通过 extern "C" 调用（应内联） |
| **环境** | BALANCE, ORIGIN, BLOCKHASH, TIMESTAMP | 5-10% | 主机 trait 对象分发 |
| **密码学** | KECCAK256, EXP | 3-8% | 库调用 |

> **重要说明：本 benchmark 的存储层是 `CacheDB<EmptyDB>`（纯内存 HashMap），不是真实的磁盘数据库（RocksDB/MDBX）。** SLOAD/SSTORE 在此测试中仅是 HashMap 的 get/insert 操作（~50-200ns/次），远快于生产环境的磁盘 I/O（~1-10us/次）。这意味着：
>
> - 本测试中存储操作的开销被大幅低估（相比生产环境）
> - JIT 的固定开销（dispatch、context marshaling）在总执行时间中的占比更高
> - 即使在存储访问已经是最快的内存操作时，JIT 仍仅有 1.02x 加速，说明 **JIT 开销本身是主要瓶颈**
> - 在真实生产环境中，存储 I/O 更慢会使两种模式都变慢，但 JIT 的固定开销占比更小，加速比可能略高

**静态分析结果**：translate.rs 中约 46 条 opcode 分支路由通过 builtins。

**Amdahl 定律推论**：从 1.024x 的总体加速比反推，内联部分约占 5-12%，builtin/共享路径占 88-95%。

**真实工作负载验证**：区块内 400 笔交易平均每笔有 28.2 条 SLOAD 和 5.8 条 SSTORE。

## 第 3 节：深度分析 - 30% 的交易为什么在 JIT 下变慢

### A 类 - 微型交易（5/23，22%）

Native 执行 <15us。JIT 每个合约入口的固定开销（1-3us）超过了执行时间本身。

## 第 4 节：JIT 开销来源

### 每个合约调用的开销（jsonl_bench.rs:698-716）

1. **字节码哈希**：`frame.interpreter.bytecode.get_or_calculate_hash()`
   - 计算 keccak256（如果未缓存）或返回缓存值
   - 成本：200-800ns（取决于字节码大小和缓存状态）

2. **HashMap 查询**：`self.functions.get(&bytecode_hash)`
   - 查询编译的 JIT 函数缓存
   - 成本：50-100ns

3. **Context 编组**：`EvmContext::from_interpreter_with_stack()`
   - 将解释器状态转换为 EvmContext 结构体（11 个字段）
   - 成本：500-2000ns

4. **主机 trait 对象分发**：`EvmContext.host` 是 `&mut dyn HostExt`
   - 每个主机调用都通过 vtable 分发
   - 成本：每次调用 5-20ns 额外开销

**对比：解释器**
- 紧密的分发循环，无哈希计算、无 HashMap、无 context 编组
- 直接对栈和内存进行指针操作

### 净收益计算

- 279 笔更快的交易：总收益 ~7.77ms
- 118 笔更慢的交易：总损失 ~6.61ms
- **净收益：~1.16ms，导致 1.02x 加速**

## 第 5 节：基准测试方法论评估

### 合理的方面

- **编译时间排除**：单独测量，使用持久化缓存
- **公平比较**：相同的 CacheDB 状态、相同的交易环境
- **真实数据**：来自 Base 主网的真实区块
- **正确性验证**：确保 gas 消耗和结果匹配

### 需要注意的限制

- **每笔交易仅运行一次**（无预热）— 利于解释器（较小的指令缓存足迹）
- **固定顺序**：总是先 native 后 JIT（可能存在顺序偏差）
- **单线程执行**
- **计时器开销**：对 4-10us 的交易来说 20-50ns 的开销显著

## 第 6 节：优化建议（按影响力排序）

### P1：内联 MLOAD/MSTORE（预期 1.15-1.25x）

**位置**：translate.rs:886-896

**现状**：当前通过 extern "C" builtin 调用

**优化**：内存操作占执行时间的 15-30%，可以内联为边界检查 + 直接内存访问（2-3 条原生指令 vs 当前 5-10 条指令开销）

**实现复杂度**：中等

```
预期改进：内联可将 MLOAD/MSTORE 开销从 ~200-500ns 降低到 ~20-50ns
```

### P2：JIT 分发缓存（预期 1.05-1.10x）

**位置**：jsonl_bench.rs:674-730（以及任何生产集成）

**优化**：将 HashMap 查询替换为最近 4-8 个字节码哈希的内联缓存（小 N 时线性搜索快于 HashMap）

**效果**：每个合约入口节省 2-5us

**实现复杂度**：容易

```
预期改进：从 ~100ns HashMap 查询降低到 ~10-20ns 线性搜索
```

### P3：消除主机 Trait 对象分发（预期 1.03-1.08x）

**位置**：revmc-context/src/lib.rs:37

**现状**：`&mut dyn HostExt` 在每个主机调用上添加 vtable 间接寻址

**优化**：通过直接函数指针在 context 中单态化热点主机操作（sload, sstore）

**实现复杂度**：容易

```
预期改进：每个主机调用节省 5-20ns
```

### P4：Gas 计量优化（预期 1.03-1.05x）

**位置**：translate.rs 的 gas 处理

**优化**：验证 LLVM IR 将 gas_remaining 保持在寄存器中。减少不必要的内存流量。

**实现复杂度**：容易

```
预期改进：减少内存往返，将 gas 检查从 ~5ns 降低到 ~2ns
```

### 前置条件：添加每操作码计时

**优化前必须完成**：添加 builtin-time vs JIT-inline-time 计数器（按操作码类别），量化实际瓶颈。

### 现实的优化目标表

| 级别 | 加速比 | 可行性 | 工作量 |
|-----|--------|--------|--------|
| 当前 | 1.02x | 已实现 | - |
| + 内联 MLOAD/MSTORE | 1.15-1.25x | 中等 | 1-2 周 |
| + 分发缓存 | 1.20-1.30x | 容易 | 1-2 天 |
| + Gas 优化 | 1.25-1.35x | 容易 | 1-2 天 |
| 理论最大值 | 1.50-2.00x | 受 builtin 调用限制 | 受架构限制 |

## 第 7 节：根本限制

### 1. Builtin 调用密集本质

**现实**：70-80% 的执行时间花在 SLOAD/SSTORE 等 builtin 调用上（本 benchmark 中是内存 HashMap 查找，生产环境是数据库查询）

**约束**：JIT **无法优化 host trait 调用路径** — 这些操作走的是与解释器相同的 extern "C" builtin 代码路径。这是固有的天花板。

**结论**：即使完全消除 JIT 开销，加速也不会超过 1.3-1.5x。

### 2. 固定分发开销

**现状**：每个合约入口成本 1-3us

**推论**：小交易（4-20us）在 JIT 下 **总是会变慢**

**解决方案**：需要启发式方法跳过简单交易的 JIT 编译

### 3. 代码大小 vs 缓存局部性

**问题**：JIT 代码比解释器循环更大，冷指令缓存对 JIT 伤害更大

**影响**：真实世界交易不在一个区块内重复

**观察**：即使排除冷启动，整体加速仍然受限

## 结论

**JIT 编译器按设计工作。** 1.02x 的结果准确反映了当前架构下 builtin 调用占主导的事实。只有 5-10% 的操作码受益于 JIT 内联，真实交易 70-80% 的时间花在通过相同 extern "C" 代码路径执行的 builtin 操作（SLOAD/SSTORE/CALL 等）上。在本 benchmark 中存储操作是纯内存 HashMap 查找，JIT 仍仅有 1.02x 加速，进一步说明瓶颈在于 builtin 调用架构本身而非存储后端。

### 实现建议

要达到现实目标 **1.2-1.3x**，实现以下两项：

1. **P1（内联 MLOAD/MSTORE）**：获得 15-25% 的额外加速
2. **P2（分发缓存）**：获得 5-10% 的额外加速

### 要点

- 当前 1.02x 加速是合理的，不是故障
- 大多数性能改进空间在 builtin 调用架构上（内联更多操作码、减少 extern "C" 调用开销）
- 短期机会有限，但中等努力的优化（内联 MLOAD/MSTORE、缓存）可达 1.2-1.3x
- 追求 >1.5x 需要更激进的架构改变（不现实）
